# ADR 0065: アカウントと関連データの削除

## Status

Accepted（Issue #1202 AC-1、Scope revision r6、2026-10-09 ユーザー判断）。Google Play の account deletion 要件の適用と、端末・運営 CN・委託先・第三者の複製・例外保持の 5 区分について、削除または保持の範囲、本人確認、鍵を失った場合、応答期限、手動の運用、件数に依存しない処理の単位を固定する。実装は #1202 の AC-2（受付）・AC-3a（端末）・AC-3b（運営 CN）が、運用の確認は AC-4 が担当する。

## Context

- kukuri のアカウントは、端末で作るアカウント鍵（secp256k1）と、その公開鍵で識別する。中央のログインは無く、Community Node（CN）にはアカウント鍵の署名で認証する（ADR 0009）。プロフィール・投稿・リアクション等は P2P で複製され、本人の端末どうしは移行と同期で同じアカウントの複製を持つ（ADR 0061・0062）。
- 既存のログアウト（`crates/desktop-runtime/src/accounts/lifecycle.rs`、`host/accounts.rs::logout_account`）は、登録簿（`accounts.json`）から外して別のアカウントへ切り替えるだけで、鍵・置き場・CN の token と同意を消さない（ADR 0047 の分類「データ非削除」）。同じ鍵を取り込み直すと、残った置き場をそのまま使ってデータが戻る。投稿の撤回（ADR 0032）は、対応する client と node が以後の表示・索引を止めるもので、複製の回収ではない。アンインストールは端末の全アカウントを消すが、他の端末・運営 CN・第三者には及ばない。
- Google Play の User Data policy の account deletion 要件（2026-10-09 確認）は、アプリ内でアカウントを作れるアプリに次を求める。
  - アプリ内の導線と、アプリを入れ直さずに使える Web の受付の両方から、アカウントと関連データの削除を依頼できること。Web の受付はメール窓口やフォームでもよく、追加の手順が要るならそれを明示する。
  - 関連データを削除すること（凍結は削除に当たらない）。委託先にも削除を依頼すること。
  - セキュリティ・不正防止・法令順守のために残すデータは、その扱いを開示すること。
  - 合理的に速く完了し、利用者に見通しを示すこと。
  - オフラインだけで作り使うアカウントは対象外とする。
- 運営 CN（`api.kukuri.app`、運営者 KingYoSun）は、GCP の 1 台の VM に Postgres・Valkey・ArcadeDB・indexer 等を置き、Postgres の `pg_dump` を毎日 GCS へ置く（作成から 30 日で削除）。公開のデータ保持ポリシー（文書版 3）は、通報 180 日・通報者連絡先 90 日・operator audit 365 日などを定める。2026-10-09 の時点で、subscriber の行（`cn_user.subscriber_accounts`）には期限も削除の経路も無く、サーバーにも `cn-cli` にもアカウント削除の操作は無い。indexer は投稿の replica と blob を自分の store に持たず、日ごとの bucket のうち当日と前日だけを 1 object ずつ読んで索引する。
- #1193 の決定（2026-10-09）は次のとおり。D9 により、アプリ内の設定から端末内の対象アカウントのデータを削除し、運営 CN へ削除を依頼できるようにする。アプリが無い人は公開 Web の受付から依頼する。運営 CN 側は本人確認の後に運営者が手動で削除する。第三者の端末・他の CN の複製は消せないと明示する。D2 により停止中の push は作らないので、通知 token は対象にならない。D3 により配布は Google Play だけとする。

## Decision

### 1. Play の要件の適用

- kukuri のアカウントは Play の app account に当たり、要件を適用する。アプリ内で作り（新規作成と鍵の生成）、端末をまたいで使い（移行と同期）、CN へ認証する仕組み（アカウント鍵の署名）を持つ。オフラインだけで作り使うものではない。中央のログインが無いことは、適用しない理由にしない。
- 削除の対象とする関連データは、運営者が管理する場所にあるもの、すなわち端末（§4）と運営 CN（§5）とする。Play の Data safety で収集と申告するデータ（申告の担当は #1203）は、§5 の運営 CN の保存に対応する。運営者が管理しない第三者の端末・他の CN・本人の他の端末の複製（§7）は、消せないことを明示する。
- アプリ内の導線（§2.1）と Web の受付（§2.2）の両方を置く。

### 2. 受付の入口（2026-10-09 ユーザー判断）

#### 2.1 アプリ内の導線

- 設定のアカウントの欄に「このアカウントを削除」を置く。対象は表示中のアカウントとする（ログアウトと同じ）。
- Android とデスクトップは、端末のデータの削除（§4）と運営 CN への依頼（§5）を出す。ブラウザ版は運営 CN への依頼だけを出し、端末のデータについてはブラウザのサイトデータの削除を案内する。その削除で同じブラウザの他のアカウントも消えることを書く。
- 確認画面に次を出す。
  - 対象のアカウント（名前と公開鍵の短縮表示）と、ログアウトとの違い（ログアウトはデータを残す）。
  - 消す前の鍵の書き出しとバックアップの案内（消すと戻せない）。
  - 消せないもの（§7）と、残すもの（§8）。
  - 運営 CN へ依頼するかの選択と、運営 CN の削除の期限（§9）。
- 確認画面では取り消せるが、実行した後は戻せない。
- 依頼の送り先は、そのアカウントの設定にある CN のうち、manifest でアカウント削除の受付を示すものとする。初回は運営 CN だけが示す。他の CN の削除は、利用者がその CN の公開文書の窓口へ依頼する。
- 実行の順は、依頼を選んだ場合の依頼の送信と受付番号の受け取り、次に端末のデータの削除とする。依頼の署名に要るアカウント鍵は、受付が終わるまで消さない。依頼に失敗したときは端末のデータを消さずに止め、再試行するか、依頼せずに端末だけ消すかを選べるようにする。

#### 2.2 Web の受付

- LP（`kukuri.app`）にアカウント削除の案内ページ（日本語と英語）を置き、Play Console の削除の URL に登録する。ページには、Play の掲載と同じアプリ名と運営者名、依頼の手順、削除と保持の範囲（§4〜§8）、期限（§9）、受付番号と状態ページの使い方を書く。
- 依頼の手順は次の 3 つとする。
  1. Android のアプリの設定から依頼する。
  2. アプリが無い人は、インストール不要のブラウザ版（`https://app.kukuri.app`）でアカウント鍵を取り込み（鍵の書き出しファイル、または別の端末からの移行）、同じ設定から依頼する。依頼の後は、そのブラウザのサイトデータを消せば鍵も消える。
  3. メール窓口（`ops@kukuri.app`）に問い合わせる。
- メールで依頼を受けたときは手順 2 を返し、署名つきの依頼で本人を確かめる。メールだけでは削除しない。
- 新しいフォーム・中央のログイン・ブラウザの新しい runtime は作らない。

### 3. 本人確認と、鍵を失った場合（2026-10-09 ユーザー判断）

- 依頼は、対象アカウントのアカウント鍵でアプリが署名する。運営 CN は署名を検証し、その公開鍵を本人確認の結果として記録する。秘密鍵は送らない。
- 依頼の受付では、その CN の最新の規約への同意を求めない（削除のために同意し直させない）。
- 運営者は、署名つきの依頼が無いアカウントのデータを、依頼を根拠に消さない。他人を装った依頼で他人の記録を消させないためである。
- 鍵を失った人は本人確認ができないので、運営 CN の削除は実行できない。期限のあるデータは期限で消え、期限の無い行（subscriber の行など）は残る。削除画面と案内ページで、鍵を持っている間に依頼するよう伝える。

### 4. 端末のデータ（区分 1）

- 担当: アプリ（共通の `ClientHost`。Android とデスクトップ）。Android の秘密の保存は、#1195 が `ClientStorage` の Android の backend として接続するもの（Keystore の鍵で包んで app-private の領域へ置く）を使い、削除も同じ `ClientStorage` の削除を通す。その backend は、対象アカウントの秘密を漏れなく消せる置き方にする（アカウントごとの Keystore の鍵を使うなら、その鍵も消す）。Web の IndexedDB の消去は、Android の削除の証拠にしない。
- 消すもの:
  - 対象アカウントの置き場 `accounts/<account_id>/` の全体。SQLite（`kukuri.db` と WAL）、iroh の store（docs・blob・endpoint の秘密鍵）、remote cache の blob、旧 store、CN の設定・discovery・購読・表示の設定、初回プロフィールと移行の journal、秘密の file 保存（`kukuri.identity-key`、`kukuri.<purpose>-<hash>`）を含む。
  - `ClientStorage` にある対象アカウントの秘密。アカウント鍵と、optional secret（private channel の capability、gossip の購読の状態、CN の token・同意・招待コード、private index の grant）を消す。消す key は、書いた key の記録（アカウントの置き場に置く）と、アカウントの記録（CN の設定、grant の行）から辿る。
  - 鍵の生成の staging（`account-transitions/`）に残る、対象アカウントの鍵の写し。
  - 登録簿の対象の行と痕跡（一覧・履歴・初回設定・作成の記録）。
  - WebView の localStorage にある対象アカウントの値（`kukuri:account:<account_id>:*`、`kukuri.metaverse.last-visited.v1:<公開鍵>:*`、対象が表示中だったときの列の下書き）。
- 残すもの: 他のアカウントの鍵・置き場・登録簿の行。端末全体の設定（アプリの同意と年齢の自己申告、テーマと言語、OS 通知の設定、ウィンドウの設定、列の配置）。起動時に消える表示用の一時ファイル（`kukuri-display/`）。利用者が自分で保存した鍵の書き出しとバックアップのファイル（アプリは消さないので、確認画面で利用者に伝える）。
- 設定から CN を外すときは、その CN の token と同意も消す（2026-10-09 ユーザー判断）。外した CN を設定に戻すと、同意し直しになる。この変更より前にデスクトップで外した CN の token と同意は、OS の keyring の値を列挙できず、記録からも辿れないため残りうる（token は 24 時間で失効する）。
- 登録簿の遷移はログアウトと同じとする（直前のアカウントへ戻り、他に無ければ新しい鍵を作る）。ログアウトの用途と挙動は変えない。
- 確認方法: 削除の後に、登録簿と一覧に対象が無いこと、対象の秘密と置き場と staging の写しが無いこと、他のアカウントの鍵と置き場がそのままであることを、desktop-runtime の契約 test と Android の実機の観測で確かめる。

### 5. 運営 CN のデータ（区分 2）

- 担当: 運営者（KingYoSun）。本人確認済みの依頼を、運営者が `cn-cli` で処理する（§9）。
- indexer は投稿の replica と blob を自分の store に持たない（bucket を 1 object ずつ読み、blob は走査のために一時取得するだけ）。消す対象は Postgres と ArcadeDB の行と、期限で消える揮発の保存に限られる。
- 結果:

| データ（保存先） | 結果 | 確認方法 |
| --- | --- | --- |
| subscriber と同意（`cn_user.subscriber_accounts`、`policy_consents`）、端末の登録（`cn_bootstrap.peer_registrations`）、認証の challenge（`cn_auth.auth_challenges`）、許可の一覧（`cn_admin.admission_allowlist`） | 消す。同意と端末の登録は subscriber の行と一緒に消える。ban 中の公開鍵は、ban の記録（公開鍵と状態）だけを ban を解くまで残す（§8） | 対象の公開鍵の行が無いこと（ban 中は状態の行だけがあること） |
| 認証の token（JWT。サーバーに保存しない） | subscriber の行を消した時点で使えなくなる（要求ごとに行を確かめる） | 消した後の要求が拒否されること |
| 投稿の索引（`cn_index.index_entries`）と検索の投影（ArcadeDB の `IndexedEntry`） | 依頼の時刻より前に作られた投稿の行を、受付の 3 日後以降に消す。その時点で該当する bucket は読取りの窓（当日と前日）から外れているので、同じ投稿は再び取り込まれない（2026-10-09 ユーザー判断） | 対象の著者の行が無いこと |
| 関係（`cn_index.relation_actions` のうち本人が当事者で、依頼の時刻より前のもの）と relation graph（ArcadeDB の `RelationUser` と辺） | 消す。集計の表（`relation_pairs`、`relation_pair_topics`、`relation_participation`、`relation_dirty_authors`）は既存の trigger と解析で追従させる | 同上 |
| 索引の申請（`cn_index.indexing_requests`）と、申請で預かった private channel の秘密（`cn_index.channel_secrets`。最後の申請者のとき） | 消す（既存の申請の取消と同じ規則） | 同上 |
| 本人が提供した信頼の観測（`cn_trust.observations` の本人が観測した行、`observation_sharing_revocations`）と relation の opt-out（`cn_trust.relation_optouts`） | 消す。他の利用者が本人を対象に提供した観測は、その利用者のデータとして既存の期限（有効 180 日、解除 30 日）まで残す（今と同じ。削除で信頼の評価を消させない） | 同上 |
| Dome の割当（`cn_metaverse.dome_hosting_assignments`。instance の manifest にチャットの履歴を含みうる） | 消す | 同上 |
| 本人や本人の投稿が対象の通報（`cn_admin.reports`）、signed moderation event と risk signal（著者の対応の `cn_safety.risk_signal_subject_authors` を含む）、送信防止の記録、operator audit、legal hold の対象 | 例外保持（§8）。著者の対応の行は、参照する risk signal が無くなったら消す | §8 の期限で消えること |
| 走査の判定と内容の cache（`cn_safety.scan_verdicts`、`content_scan_cache`） | 索引の行が消えて参照されなくなったものを、索引の保持期間（現在の設定で 30 日）の回収で消す | — |
| topic rendezvous と presence（Valkey。公開鍵を持たない）、補助 index の記録（メモリだけに置く） | 期限で消える（45〜60 秒、1 時間） | — |
| ログ（コンテナの出力）、backup（GCS の `pg_dump`） | 例外保持（§8）。個別には消さない | — |
| 本人が出した通報、tester feedback、権利侵害申出 | 公開鍵を持たずアカウントから辿れないので、依頼では消さない。期限（通報 180 日・連絡先 90 日、feedback 180 日、申出は ADR 0034 の期間）で消える | — |

- 削除の後に他の利用者が行った公開の操作（本人へのフォローなど）は、その利用者のデータとして扱い、取り込みうる。
- 削除の後に同じ鍵で再び認証すると、新しい subscriber の行ができる（新しい利用として扱う）。ban 中の公開鍵は、ban の記録が残るので認証できないままになる。

### 6. 委託先（区分 3）

- 担当: 運営者。
- 結果: 削除の依頼を送る必要がある委託先は無い。根拠は次のとおり（2026-10-09 確認）。

| 事業者 | 渡るもの | 結果 |
| --- | --- | --- |
| Google Cloud（VM、永続 disk、GCS の backup、Secret Manager、ログを送る場合の Cloud Logging） | 運営 CN のすべての保存（§5）。Secret Manager には利用者のデータを置かない | 運営者が自分の資源の中で消す（§5）。backup とログは §8 の期間で消える。Google への個別の依頼は要らない |
| OpenAI（Moderation API） | 投稿の本文、静止画、動画から抜いた画像。公開鍵などの識別子は送らない | OpenAI はこの API に送った内容を保持しない（不正利用の監視のための保持も、処理の状態の保持も無い）。依頼は要らない |
| Canadian Centre for Child Protection（Project Arachnid Shield） | 走査するメディアのバイト列、または PDQ hash。識別子は送らない | アカウントに結び付かないので、アカウント単位の依頼の対象にならない。扱いは同団体の方針に従う |
| Google Workspace（`ops@kukuri.app` のメール） | メールで寄せられた問い合わせ | 運営者が、依頼の記録と同じ期間（§8）で消す |
| Cloudflare（LP とブラウザ版の配信、DNS） | 配信の要求（IP address 等）。アカウントに結び付かない | 対象外 |
| GitHub（配布物と更新確認、Issue） | 配布物の取得の要求と、利用者が自分で投稿した Issue | 対象外。Issue は利用者が GitHub の機能で消す |

- 以前に使った自前の VLM（さくら VPS を経由。2026-09-17 に停止）には、今は送らない。

### 7. 第三者の端末・node の複製（区分 4）

- 担当: なし（運営者もアプリも消せない）。アプリと案内ページは、消せないことを明示する。
- できること:
  - 削除の前に既存の投稿の撤回（ADR 0032）とプロフィールの編集をすれば、対応する client と node は以後の表示と索引を止める。確認画面で案内する。削除の後は鍵が無いので、撤回も編集もできない。
  - 運営 CN の分は §5 で消す。
- 保証できないこと（消えないもの）:
  - P2P で受け取った相手の端末の複製（公開投稿、プロフィール、リアクション、添付、カスタムリアクションのセット）、DM の相手の複製、private channel の参加者の複製。
  - 他の CN の索引・cache・記録（その CN の窓口へ依頼する）。
  - 本人の他の端末（移行と同期の複製）と、別のブラウザのブラウザ版。それぞれの端末で消す。
  - Mainline DHT の参加者、relay、経路事業者の記録。DHT の告知と補助 index の record は期限で消える。
  - 利用者が自分で保存した鍵の書き出しとバックアップのファイル。
- 確認方法: 管理しない場所なので確認しない。第三者の P2P の履歴を取り寄せて確かめることもしない。

### 8. 例外保持（区分 5、2026-10-09 ユーザー判断）

依頼を受けても、次は記載の期間まで残す。残すのは安全・法務・復旧の記録に限る。

| 種類 | 理由 | 期間 |
| --- | --- | --- |
| 本人や本人の投稿が対象の通報（異議申立てを含む）と通報者連絡先 | 安全性の対応と異議申立て | 通報 180 日、連絡先 90 日 |
| signed moderation event と risk signal（著者の対応を含む） | 安全性の判定と異議申立て | 180 日。risk signal は失効が早ければそれまでとし、異議申立ての通報が参照する間は残す |
| 他の利用者が本人を対象に提供した信頼の観測（ブロック・ミュート） | 安全性の評価（削除で評価を消させない） | 有効なもの 180 日、解除されたもの 30 日 |
| 送信防止の記録（対象は投稿と blob で、公開鍵を持たない） | 法的な措置の継続 | 既存の規則のまま（定期の削除は無い） |
| operator audit（削除の実施の記録を含む） | 運営者の操作の説明責任 | 365 日 |
| ban の記録（公開鍵と状態） | 不正防止（削除で ban を解かせない） | ban を解くまで |
| legal hold の対象 | 法的手続き | hold の解除まで |
| ログ（コンテナの出力。endpoint ID 等を含みうる） | セキュリティと障害の調査 | 接続ログの公開値は 30 日。今の実装はサイズで回る（コンテナごとに 20 MB × 5）ので、AC-3b で公開値と一致させる |
| backup（GCS の `pg_dump`） | 障害からの復旧 | 作成から 30 日。その後も GCS の既定の復元の猶予（7 日）の間は残る。個別には消さない |
| 削除の依頼の記録（受付番号、公開鍵、状態、区分ごとの結果、日時）と、メールのやり取り | 対応の証拠と状態の確認 | 完了から 1 年 |

- 利用者向けの説明: 確認画面と案内ページに、残す種類・理由・期間を書く。運営 CN の公開文書（データ保持ポリシー）にも同じ値を載せる。今の公開文書には backup と tester feedback の日数が載っていない。

### 9. 期限・状態・手動の運用（2026-10-09 ユーザー判断）

- 期限: 受付（運営 CN が署名を検証して記録した時点）から 30 日以内に完了する。索引の再取り込みを避けるため、処理は受付の 3 日後から始める。
- 受付の直後に、受付番号と確認用の秘密を 1 回だけ表示する。CN は秘密の hash だけを持つ。アプリは控えを促し、案内ページは状態ページの使い方を示す。
- 状態ページ（運営 CN）は、受付番号と秘密を受けて、状態・更新時刻・公開の文言を返す（権利侵害申出と同じ形）。番号と秘密が合わないときは、存在しない番号と同じ応答にする。
- 状態は次のとおりとする。
  - 受付済み: 署名を検証して記録した。
  - 処理中: 運営者が処理を始めた。
  - 一部未完了: 失敗した区分を記録した。再実行で、記録した区分から再開する。
  - 完了: 消す区分をすべて消した。
  - 完了（例外保持あり）: 消す区分をすべて消し、残した種類と期限を公開の文言で示す。
- 手動の運用:
  - 運営者は `cn-cli` で、依頼の一覧（期限の近い順）・詳細・処理の実行・状態の更新を行う。
  - 処理の実行は §5 の区分を順に §10 の単位で消し、結果を依頼の記録と operator audit に残す。手順は runbook に置く（AC-3b）。
- backup から戻したときは、API を公開する前に、戻した DB にある未完了の依頼を処理し直す。backup の作成より後に受け付けた依頼は失われる。状態ページで見つからない受付番号の問い合わせはメール窓口で受け、署名つきの依頼を出し直してもらう（鍵が無ければ実行できない）。

### 10. 件数に依存しない処理の単位

- 受付と状態の確認は、対象のデータの量に関係なく、依頼の記録 1 件の読み書きで終える。全件の取得や全履歴の同期を待たない。
- 端末:
  - 確認画面の実行で行うのは、依頼の送信（選んだ場合）、登録簿の更新（対象を外して削除待ちに積み、ログアウトと同じく別のアカウントへ切り替える）、秘密の削除まで。置き場のファイルは、対象の runtime を止めた後に背景で消す。
  - 置き場の削除は 1 回 256 項目まで。ディレクトリを読みながら消すので、続きの位置はディレクトリ自身が持つ。
  - 削除待ちは登録簿に置き、起動のたびに再開する。同時に動かすのは 1 件。
  - 失敗は削除待ちに残して表示し、設定の再試行か次の起動で再開する。自動の無期限の再試行はしない。削除待ちの行は完了で消す。
  - 秘密の削除の回数は、対象アカウントが書いた key の数だけで決まり、他のアカウントの数には依らない。
- 運営 CN:
  - 処理は区分ごとに、公開鍵の索引で 1 transaction 128 行まで消す。区分と進みを依頼の記録に残し、止まっても記録した区分から再開する。消した行は残らないので、同じ区分の再実行は安全である。同時に処理する依頼は 1 件とする。
  - 著者の公開鍵の索引が無い保存先（`index_entries`、`relation_actions`、`indexing_requests`、`dome_hosting_assignments`、ArcadeDB の `IndexedEntry`）には、AC-3b で索引を足す。全表の走査では消さない。
  - 削除の確認は、管理する保存先の対象の行の有無と処理の記録で行う。第三者の P2P の履歴を取り寄せない。全投稿の ID の削除台帳や、全体の再索引を前提にしない。

## 採らない方式

- Web のフォームで依頼を受け、後から署名で本人を確かめる方式（2026-10-09 不採用）。フォームと未確認の依頼の管理が増え、鍵を失った人を救えない点は、署名に一本化した方式と変わらない。
- 運営者が提出された情報（公開鍵・表示名・投稿の内容など）で本人と判断する方式（2026-10-09 不採用）。他人を装った依頼を見分けられない。
- 索引をすぐに消し、著者単位の抑止の記録と取り込みの gate を足す方式（2026-10-09 不採用）。受付の 3 日後に消せば、記録も gate も無しで再取り込みが起きない。
- 秘密鍵の提出、中央のログイン、ブラウザの新しい runtime。
- 削除の依頼をもとに、運営 CN が他の CN や第三者の端末へ削除を求めること。ネットワーク全体を統べる権限は存在しない（`docs/architecture/p2p-first-community-node-responsibility-boundary.md`）。
- 削除の時に自分の投稿をまとめて撤回すること。依頼されておらず、撤回は既存の機能で削除の前に行える。

## Consequences

- アプリ内（Android）と Web の両方の受付を、秘密鍵の提出も中央のログインも無しで用意できる。
- 鍵を失った人は運営 CN の削除を依頼できない。期限の無い行（subscriber の行など）は残る。
- 運営 CN の削除は、早くても受付の 3 日後になる。
- 設定から CN を外すと、その CN の token と同意も消え、戻すと同意し直しになる。この変更より前にデスクトップで外した CN の分は、OS の keyring に残りうる。
- 運営 CN に、削除の依頼の記録という新しい保存ができる（完了から 1 年）。
- 障害で backup から戻したとき、backup の作成より後に受け付けた依頼は失われる。
- 運営 CN の公開文書が示す保持期間と実際の保持を、AC-3b で一致させる。

## Data classification

### 削除の依頼の記録（運営 CN）

- Feature 名: アカウント削除の依頼の受付と処理の記録
- Durable / Transient: Durable（完了から 1 年）
- Canonical Source: 運営 CN の Postgres（その node だけに置く）
- Replicated?: No
- Rebuildable From: 再構築しない（署名つきの依頼と、運営者の処理の記録）
- Public Replica / Private Replica / Local Only: Local Only（その node だけ）
- Gossip Hint 必要有無: 不要
- Blob 必要有無: 不要
- SQLite projection 必要有無: 不要
- 必須 contract: 署名の検証（他の鍵の署名や改ざんした依頼を受け付けない）、最新の規約への同意を求めないこと、受付番号と秘密の hash、状態の遷移、区分ごとの進みと再開、1 transaction の上限、受付の 3 日前は索引を消さないこと、ban の記録を残すこと
- 必須 scenario: アプリ内の依頼 → 受付番号 → 運営者の処理 → 状態ページで完了（AC-4 の dry run）

### 端末の削除待ちと、書いた秘密の key の記録

- Feature 名: 端末のアカウントの削除
- Durable / Transient: Durable（削除待ちの行は完了まで。key の記録はアカウントの置き場と一緒に消える）
- Canonical Source: `accounts.json` の削除待ちの行、アカウントの置き場の key の記録
- Replicated?: No
- Rebuildable From: 再構築しない
- Public Replica / Private Replica / Local Only: Local Only
- Gossip Hint 必要有無: 不要
- Blob 必要有無: 不要
- SQLite projection 必要有無: 不要
- 必須 contract: 他のアカウントを消さないこと、1 回の上限、停止からの再開、依頼の受付の前に鍵を消さないこと、依頼の失敗で端末のデータを消さないこと、CN を外すと token と同意が消えること
- 必須 scenario: 2 つのアカウントで片方を消し、もう片方が残る。途中で止めて再起動すると完了する
