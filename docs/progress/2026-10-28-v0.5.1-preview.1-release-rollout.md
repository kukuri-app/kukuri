### Release run の再実行

Release run は attempt 1・2 とも `linux-package / linux-appimage` の Real app tests の `live-overlay-push` だけで失敗した。送信側の押下から描画までの p95（上限 100 ms）が 117・109 ms だった。他の package と検証の job は attempt 1 で成功し、Release は作られていなかった。

Release だけが使う ubuntu-22.04 で、同じ Linux package を 3 つの source で同時に dispatch して切り分けた（`signing=distribution`、公開はしない）。

| source | live-overlay-push の wall p95 | 結果 |
| --- | --- | --- |
| `v0.5.0-preview.1`（v0.5.0 の Release では 86・85 ms で成功） | 104・103 ms | 失敗 |
| `c16e49f32`（メディアカラム #1968 の直前） | 112・98 ms | 失敗 |
| `b48e7e87a`（今回の固定 source） | 55〜62 ms | 成功 |

同じ source でも runner によって入力・描画・smoke の時間がおよそ 2 倍違い、v0.5.0 の source でも上限を超える。今回の差分による劣化ではなく、22.04 の runner の速さの違いで上限をまたいだと判断した。同じ run の失敗 job の 3 回目の再実行（attempt 3）で 73〜77 ms となり、linux-appimage を含む全 job（changelog・release-assets・publish-draft・verify-published）が成功した。Windows と CLI の成果物は attempt 1 のもの。

2026-10-29 の調査で、差の原因を特定した。runner の速さ全般ではなく、22.04 の WebKitGTK 2.50.4 が、GPU の無い環境で Push の回数と状態の文字が変わるたびに window 全体を描き直すことが原因だった。押下はその描画の後ろで待つ。描き直しの重さが CPU の型によって変わり、上限 100 ms をまたいでいた。同じ CPU の型でも、24.04（2.52.6）は変わった部分だけを描き直し、16〜22 ms だった。22.04 だけ、発行待ちを含む上限を 200 ms にした（`docs/runbooks/dev.md` の `live-overlay-push`）。
