# #1221 R2-B: CN session の期限処理・回復を node 別差分へ変更

## 完了境界

正本は [#1221](https://github.com/kukuri-app/kukuri/issues/1221) の R2-B と、2026-09-27 のユーザー決定「R2-B CNごとの失敗・回復・確認」、
2026-09-25 のユーザー決定「R2-B 着手順」(R5-H の後)。基準は #1378 merge `10abf86a`。依存の R2-A・R5-H は完了済み。
仕様は [ADR 0055 §3.1](../adr/0055-demand-owned-network-work.md)。

- 期限の来た node と、その node の分だけを扱う。1 node の 401・同意の解除・失敗は、別の node の認証・接続・購読を
  再起動しない。成功は対象の protocol の実際の結果(gossip の neighbor の成立)で判定する。
- 撤去: 15 秒ごとの全 node の session job による期限前の HTTP(公開 policy と同意の状態の GET)、scheduler の
  Connectivity job(全体の sync status の snapshot)、self-heal(`maybe_self_heal_community_node_connectivity`・
  `repair_community_node_connectivity`・全 ready node の force refresh・force の全体再適用と作り直し)、
  本番で使われていない `reapply_community_node_connectivity`、全 node の合成と前回の適用状態・版、
  rendezvous の peer の全体の seed への合流、seed の更新による全 topic への join、relay の集合の変化ごとの作り直し、
  再接続の状態と guard。
- 維持: 画面の手動の回復操作(`refresh_community_node_metadata`)、`Direct P2P → Relay Supported P2P → Relay Fallback`、
  未同意の node への I/O 0、R2-C の lease(endpoint の世代が変わった時だけ lease の task を作り直す)。
- 範囲外: R2-D(通信状態の集計・表示)、CN のサーバ側、新しい UI。

| --- | --- | --- |
| AC-1 | tick ごとに期限の来た node の session job だけを積み、期限前の node へは HTTP を送らない(policy と consent の GET を含む)。観測の送信は node ごとの lane | desktop-runtime `tick_work_does_not_grow_with_failure_or_dormant_history`(idle の tick は観測の lane 2 本だけ・HTTP 0、期限の来た登録で同意の確認 0)、`a_failing_node_never_touches_the_healthy_node`(期限前の HTTP 0)、`maintenance_tasks::blocked_lanes_do_not_stop_other_nodes_or_duplicate_work` |
| AC-2 | 5xx・通信失敗・再試行中は、その node の phase と backoff だけを変え、relay と seed を残す。外すのは同意の解除・認証の失効(401 の後の再認証の失敗)・設定からの削除だけ。ある node の成功で別の node の gate を開かない | `a_failing_node_never_touches_the_healthy_node`、`connectivity_apply_keeps_only_the_node_with_verified_ready_session`、`community_node_connectivity_filter_is_scoped_per_node`、`banned_member_with_stored_token_stops_self_heal_reauthentication` |
| AC-3 | `node → {relay, seed}` の差分だけを transport・docs・blob へ適用する。rendezvous の peer はその topic だけへ join する。relay の変化はその場で入れ替え、作り直しは既存の endpoint を使えないときだけ。設定の変更と消去は、外した node だけを触る | `peer_delta_is_scoped`、`a_failing_node_never_touches_the_healthy_node`(generation・join の回数)、`tick_work_does_not_grow_with_failure_or_dormant_history`(外した node の履歴)、stack `relay_set_changes_in_place_and_only_a_connect_mode_switch_rebuilds`、transport `rendezvous_peers_join_only_their_topic_once` |

| AC-5 | 正常な CN と失敗する CN の同居。B の出来事で A への HTTP・stack の generation・A の topic への join・lease の task の作り直しが増えない。期限前の HTTP 0。V2・V3 の 10 倍で 1 tick の仕事が変わらない | 上の desktop-runtime 3 件と transport 2 件。mutation check は下記 |
| AC-6 | ADR 0055 §3.1 と検証表(NW-5・NW-6 の実試験名)、本文書 | — |

## 入口と副作用

| 入口 | helper | 結果 |
| --- | --- | --- |
| scheduler の tick / `run_community_node_session_maintenance_once` | `community_node_maintenance_jobs`(`CommunityNodeSessionState::due_at`) | 期限の来た node の session job と、node ごとの観測の lane |
| session job・索引申請の更新・観測の送信(Ready で token が有効) | `ensure_due_community_node_session` | 期限の来た heartbeat・metadata・rendezvous だけを送る。403 で再同意が要れば Idle にして relay・seed を外す |
| それ以外の session job・利用者の操作(検索・通報・手動の回復など) | `ensure_community_node_session`(preflight → 認証 → 同意の確認 → 登録) | Ready になったら、その node の relay・seed を差分で足す |
| 401 の後の再認証 | `reauthenticate_community_node` | 失敗したら認証の失効として、その node の relay・seed・候補を外す |
| metadata の更新・Ready への遷移 | `sync_community_node_connectivity` → `apply_community_node_connectivity` | その node の寄与を入れ替え、和が変わったときだけ endpoint・transport・docs・blob へ適用する |
| rendezvous の応答 | `HintTransport::join_topic_peers` | 鍵から引いた topic だけへ、まだ知らない peer を join する |
| 同意の撤回・token の消去・設定からの削除 | `deactivate_community_node_connectivity`、`forget_community_node` | その node の relay・seed・受信と rendezvous の候補(と session)だけを外す |
| 利用者の seed の設定 | `apply_community_node_connectivity(None)` | 同じ和を適用し直す(docs の probe の失敗なら作り直す) |
| gossip の topic の受信 task | `topic_rejoin_window` | neighbor の無い間だけ、rendezvous の候補と seed・ticket の窓から最大 4 件へ再 join。seed が増えたら次の再 join を早める |

  - `session_runtime_support.rs`: scheduler と背景の lane の Ready の分岐(`ensure_due_community_node_session`・
    `ready_community_node_token`・`note_community_node_token`)、

    `apply_community_node_connectivity`)。`active_community_node_connectivity_config` と
    `apply_runtime_connectivity_assist`・`apply_effective_seed_peers`・force の各版を削除。
  - `session_state_support.rs`: Retrying では確認済みの状態を捨てない。
  - `requests_support.rs`: `reauthenticate_community_node`、登録の更新が「再同意が要る」を返す、rendezvous の topic ごとの join、

## 検証(局所)

- 変更前に失敗する条件: 変更前の実装で、`a_failing_node_never_touches_the_healthy_node`(期限前に両 node へ 6 本ずつの HTTP)、
  `peer_delta_is_scoped`(rendezvous の peer を topic へ join しない)、`tick_work_does_not_grow_with_failure_or_dormant_history`
  (期限前に HTTP)の 3 件が失敗した。
- desktop-runtime `cargo test -p kukuri-desktop-runtime --lib` 317 件成功(本条件の 3 件、stack の 1 件を含む)。
- transport `cargo test -p kukuri-transport --lib` 139 件成功(`topic_rejoin` の 2 件を含む)。
- app-api `cargo test -p kukuri-app-api --lib` 448 件成功。harness `RUST_MIN_STACK=67108864 cargo test -p kukuri-harness --lib -- --test-threads=1`
  23 件成功。CLI `cargo test -p kukuri-cli --no-fail-fast` 全件成功(Windows では `process_e2e` は 0 件。Linux の `process_e2e` は Docker `rust:1.92.0-bookworm` で 5 件成功)。
- scenario(`CN_POSTGRES_PORT=55433`): `community_node_public_connectivity`・`community_node_index_query_client`・
  `community_node_report_routing`・`community_node_trust_relation_client`・`cargo xtask e2e-smoke` が成功。
- `cargo fmt --all --check`、`cargo clippy -D warnings`(transport・desktop-runtime・harness・cli・app-api の all-targets)、
  `cargo xtask oversized-files`(違反 0)。IPC の型と CLI の command は変えていない。
- mutation check(外すと失敗することを確かめ、元に戻した):
  - desktop-runtime: 一時的な失敗で relay・seed を外す(AC-2)、再認証の失敗で外さない(AC-2)、期限を見ずに session job を積む(AC-1)、
    Ready の分岐を外して毎回同意と policy を確かめる(AC-1)、設定の変更で全 session を消す(AC-3)、rendezvous の peer を全 topic へ
    join する(AC-3)、relay の集合の変化ごとに作り直す(AC-3)、seed の設定で全 topic へ join する(AC-3・AC-4)。
  - transport: neighbor のある topic も再 join する、再 join をしない(AC-4)、rendezvous の peer を全 topic へ join する、
    同じ peer を何度も join する(AC-3)。
- 試験の書き換え: 全 node の合成・前回の適用状態・版・強制の再適用を読んでいた試験は、node ごとの寄与(`community_node_connectivity`)と
  transport の discovery の状態を読む形へ改めた。強制の再適用の試験(`reapply_community_node_connectivity_forces_unchanged_runtime_inputs`)と
  relay の比較だけの単体試験 3 件は撤去し、stack の実 endpoint で relay の入れ替えと作り直しの条件を確かめる 1 件へ置き換えた。
  endpoint の作り直しの試験(host)は、直接だけから relay つきへの切替で作り直す形にした。

## 固定 head 監査(`8ed35e37`)の blocker と修正

監査は FAIL(blocker 3 件)。3 件とも修正前に失敗する試験を置き、修正後に通ること、修正を外すと失敗すること
(mutation check)を確かめた。

| ID | 原因 | 修正 | 試験 |
| --- | --- | --- | --- |
| B1 | 観測の提供の有効化が、任意文書を手元の同意へ足した後も、確認済みの状態(`current_policy_verified_for`)を古い同意のまま残していた。Ready の分岐はこれを更新しないので、次の期限の登録でその CN の relay・seed が外れ、`authenticated` も偽になった(base からの退行) | 同じ操作の中で、確認済みの状態が追記前の同意と一致していれば、追記後の同意へ揃える | `trust_observations::enabling_sharing_keeps_the_node_connectivity_after_a_due_registration` |
| B2 | token の期限の更新(と初回)で参加を拒否(BANNED)されると AwaitingAdmission になるが、relay・seed を外していなかった。AwaitingAdmission は期限を持たないので、その後も外れない | `set_community_node_admission_rejection` で、経路によらずその node の relay・seed・候補を外す | `node_isolation::admission_rejection_on_token_refresh_drops_the_node_connectivity` |
| B3 | 観測の lane(と索引の grant の更新)は、Ready でない node では完全な session の確立へ落ち、再試行の gate より前に `GET /v1/policies` を送っていた(Retrying は 15 秒ごと、参加の拒否・再同意の待ちは無期限) | `ensure_due_community_node_session` は、Ready でない node の期限(`due_at`)が来ていなければ要求を送らず `Deferred` を返す | `trust_observations::a_retrying_node_gets_no_request_from_the_observation_lane_before_due` |

## 既知の制約

- scheduler の tick は 15 秒のまま。tick ごとに、設定した node の数だけ期限を評価し、観測の状態 file を node ごとに読む
  (HTTP は送信待ちがあるときだけ)。node の数は利用者が設定した件数。
- 一時的な失敗(Retrying)の間は、確認済みの状態を保つので status の `authenticated` は真のまま。
- 同意を撤回した CN から得た rendezvous の候補は忘れるが、既に neighbor になった peer との gossip の接続は切らない
  (gossip に peer 単位で外す API が無い)。
- rendezvous の peer は、その topic の gossip だけへ渡す(docs・blob の seed には入れない)。docs の読み手は topic の neighbor
  (R5-H の `topic_read_candidates`)から選ぶ。
- 候補の無い topic の再 join の間隔も 64 秒まで伸びる。seed が増えたときと rendezvous の候補が届いたときは待たずに join する。
- `restart_required` は「その node の確認済みの relay のうち、endpoint に入っていないものがある」の意味になった。
- 同じ topic を複数の CN が rendezvous で返すときは、取得元の CN ごとに候補を覚え、合わせて topic あたり 4 件まで。
- 参加中の private channel の rendezvous の鍵は、参加中の channel(lease の 64 件以内)から導く。
