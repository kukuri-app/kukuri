## 観測・証跡

同じ検証画像1件（PNG 1,770,843 bytes、BLAKE3 `665199e0604a81268057f89759ff5de7bdfde6d44319225e871085255928e3d2`）を使う。保持端末はCNを使わず、別topicに公開参照を持ち、本番DHT/index/relayで告知する。投稿者の既知nativeから受信側へ署名済みpostと公開参照を渡し、画像取得前に投稿者を停止する。投稿は専用topic `kukuri:topic:release-1657` で、実利用者のprofileは使わない。

- Dockerの保持端末では送信先ごとにNATのportが変わり、登録したaddressとDHTのaddressが一致せず告知をやり直していた。この組み立ての失敗を製品の取得成功率へ加えていない。対応機能は追加していない。
- Windowsネイティブの保持端末では告知成立を確認し、native CLIが14,387msで画像を取得。hash/sizeだけでなく元PNGとのbyte一致も確認。
- 同じ条件の別native profileでの取得は15,547msと24,041msでpayload無し。前者の60秒pcapはDHT 238,865 IP bytes、index 4,329、その他UDP 154,728、後者はDHT 117,782、index 3,960、その他UDP 46,664。成功試行の通信量・転送経路と候補消費数は未計測であり、推測をPASSへ置換していない。
- 同じ条件の3番目のnative CLI profileでは15,427msでpayload無し。60秒pcapはDHT 271,411 IP bytes、index 2,784、その他UDP 330,332。Linux CLIの有効な試行は1/4成功（25%）。1要求は30秒内の結果で、各profileの初回取得と明示した再試行を区別し、受信済みcacheを成功へ加えない。
- CLIはtracing subscriberを初期化しないため、RUST_LOGを指定しても取得行が出ない。製品の計測を追加せず、固定sourceのnative runtimeを既存public-blob E2Eと同じconstructorで起動し、既存tracingを初期化するGit除外の操作補助で補完。Windowsで5,299msの取得成功、元PNGとbyte一致。既知候補は`selected_peer_count=1`、停止済み投稿者のConnectTimeoutが1件、未知の保持端末で成功した1件を足して消費2件。DHTはaddressを2件返し、indexが保持端末のendpointを返した。CLIとはrelay設定の条件が違うため、成功率を混ぜない。この成功試行の実転送経路は未計測。
- Webの専用profileでversion 9と本番nodeの文書へユーザー承認に基づいて同意。最初は投稿者の停止前に画像が取得されたため、観測から除外。同じ画像投稿の後に専用topicへ15件の無画像投稿を置き、新しい検証profileへmetadataを受信させ、取得前の画像無しを確認した。投稿者を停止した後に画像投稿をviewportへ入れ、43,219ms後の確認で768×768の画像表示を確認（成功1/1、既存再試行を含む観測上限であり、最初の要求の正確なlatencyではない）。`web-image-observed.png`へ画面を保存。
- 操作補助から`chrome://webrtc-internals`を開く操作はブラウザーのURL制限で拒否されたため、迂回せずユーザーへChromeでの観測を依頼した。画像が出たことだけで実転送経路を推測せず、以下のユーザー観測を記録した。
- Linuxの同じnative runtime操作補助は5,515msで取得成功、PNGのbyte一致。消費は既知1件の失敗と未知の保持端末1件の成功で2件。約11.05秒のpcapではDHT 651,236 IP bytes、index 3,154、その他UDP 1,795,813、TCP/443 57,632。保持端末のUDP socket（PID/portも照合）からの受信は1,718,749 IP bytes、relayからのTCP受信は計31,955 IP bytesで、実データは保持端末との直接UDPを主体に転送された。接続補助ではrelayにも通信した。captureはkernelで168 packetを落としており、bytesは下限の概算。画像hashの`get_peers`要求は162 packet、22,842 IP bytes（UDP payload 18,306 bytes）。DHT総量には一覧・endpoint・topicの処理も含む。
- captureのbufferを増やした別profileの同条件試行は5,442msでpayload無し。既知の候補1件がConnectTimeout、DHTで返った3 addressから保持端末のendpointは得られず、消費1件。pcapはkernel drop 0、DHT 380,551 IP bytes、index 369、その他UDP 19,763、TCP/443 19,724。画像hashの`get_peers`要求は83 packet、11,703 IP bytes（UDP payload 9,379 bytes）。このLinux runtime条件は1/2成功（50%）で、CLI条件・Windows条件と混ぜない。
- ユーザーのChromeシークレットsessionでも画像表示を確認。通常tabは既に閉じていたとの申告。検索APIの呼出しは0で、DataChannelの累積受信は添付graphで約3MB。この時間帯は操作補助側の取得済みWeb profileが同topicで稼働していたため、既知peerによる取得の可能性があり、未知の保持端末を検索した結果として扱わない。操作補助のWeb tabを閉じ、新しいsecret sessionへ投稿者からmetadataだけを渡し、画像をviewportへ入れる前に投稿者を停止した。ユーザーが検索と受信量を観測中。
