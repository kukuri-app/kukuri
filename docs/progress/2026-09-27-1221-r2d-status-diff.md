# #1221 R2-D: 通信状態の集計・表示を差分と有限ページへ変更

## 完了境界

正本は [#1221](https://github.com/kukuri-app/kukuri/issues/1221) の R2-D と、2026-09-27 のユーザー決定「R2-D 通信状態の表示」。
基準は #1379 merge `7aec766d`。依存の R2-A・R2-B・R2-C は完了済み。仕様は [ADR 0055 §3.2](../adr/0055-demand-owned-network-work.md)。

- 通常の通信状態(`get_sync_status`)は、件数と稼働中の topic(lease の 64 件と短期の送信先 16 件)だけを返す。
  peer の一覧は、設定画面の詳細を開いたときだけ `list_connectivity_peers` のページ(1 回 64 件まで)で読む。
- 状態の読取りは、seed・台帳・SQLite・keyring を読まず、取得の候補の cursor を進めない。
- 撤去: 3 秒ごとの全体の pull と全体の等値比較(WP-B13 の Decision は失効)、host の最新 event の再送、
  状態の表示を流用した読取り 4 件。
- 維持: frontend の 60 秒ごとの読み直し(push の取りこぼしの補い)、CN の状態の読取り(`get_community_node_statuses`)。
- 範囲外: R6-A、UI の全面改修。

- transport: `status_changes.rs`(`StatusKey`・`StatusChanges`)。`PeerSnapshot`・`TopicPeerSnapshot`・`DiscoverySnapshot` を件数へ。

  (`configured_peer_ids`)と一覧の clone を撤去。`PeerAddrBook::available_peer_ids` は `preferred` を返す。計測用の
  `status_read_steps`(`test-support` feature)。store: `imported_peer_candidate_ids`(折り返さないページ)。
- app-api: `SyncStatus`・`TopicSyncStatus`・`DiscoveryStatus` を件数へ。`sync_status_delta`、`active_gossip_disabled_scopes`、
  `list_connectivity_peers`・`ConnectivityPeersRequest`・`CONNECTIVITY_PEER_PAGE_LIMIT`。`SyncClock`(`last_sync_ts`)、
  `with_status_changes`。`normalize_topic_diagnostics` の O(n²) の和を撤去。
- desktop-runtime: `sync_status_observer.rs` を差分の push へ書き換え、`RuntimeEvent::SyncStatusChanged` に
  `removed_topics`・`removed_community_nodes`。`CommunityNodeSessions`。stack は `StatusChanges` を作り直した transport へも渡す。
  host の `ClientEventState` と再送を撤去(`ClientEventReceiver` は broadcast の受信者)。
- docs-sync: remote の読取りの成功を `PeerAddrBook` の観測へ記録する。
- Tauri: `list_connectivity_peers`。背景通知は `local_author_pubkey`。CLI: `list_connectivity_peers`、`get_sync_status` の schema、
  `command-parity.json`。
- frontend: `applySyncStatusDelta`・`mergePulledSyncStatus`、`PeerPageList`・`SettingsDetails`(開いている間だけ中身を描く)、
  `listConnectivityPeers`(runtime・mock)。`formatListLabel`・`mergeCommunityNodeStatuses`・`effectivePeerIds` を撤去。

## 検証(局所)

- 変更前に失敗する条件: 変更前の実装では、状態の読取りが docs/blob の補助を `ranked_peers` 経由で読み(候補の cursor を
  進め、SQLite の 3 表を読む)、transport が seed と取り込んだ ticket の窓を SQLite から読んでいた。3 秒ごとに全体を作り
  直し、変化の無い間も読取りの仕事があった。
- mutation check(該当部分を一時的に外すと失敗し、元に戻した):
  - transport: 補助を `ranked_peers` で読む(AC-2)、`configured_peer_count` で SQLite を読む(AC-1・AC-6)、ページの
    cursor を含む範囲にする・SQL の `>` を `>=` にする(AC-3)、受信 task の印を外す(AC-4)。
  - app-api: gossip の停止を全件で返す(AC-1)、差分で印の topic へ絞らない(AC-4)、ページの上限を外す(AC-3)。
  - desktop-runtime: 1 秒のまとめを外す、印を無視して全 topic を送る、CN の session の印を外す(AC-4・AC-6)。
  - frontend: 詳細を閉じていても描く、差分で topic を置き換える、ページを追記しない(AC-3・AC-4)。
- 実行した検証の結果は PR の本文に記す。

## 既知の制約

- `get_community_node_statuses`(60 秒の読み直しと CN の画面)は、設定した node ごとに同意・token の file か keyring を
  読む。R2-D の差分の push は、印の付いた node だけを読む。
- 補助の数は、取得の成功を観測した peer(最大 2 件)の数。remote の docs の読取りが成功するまで、docs の補助は 0 のまま。
- 設定済みの peer の数は、設定した seed と CN の seed の数の和(同じ peer が両方にあれば 2 と数える)。取り込んだ
  ticket は詳細のページで読む。
- 印が 256 件を超えたときは全 topic を送るが、抜けた topic は 60 秒の読み直しまで画面に残る。
- 経路の種別(relay だけか)は、状態を作るときに接続中の peer ごとに `remote_info` の保持中の path を見る(生存の判定には
  使わない)。経路の変化だけでは push しない。
